# Task Description

## 1. Постановка задачи

Проект реализует MVP MLOps-системы для потоковой обработки табличных страховых данных Ethiopian Insurance Corporation.  
Целевая задача: бинарная классификация, где по историческим данным страховых полисов и заявок прогнозируется целевая переменная `CLAIM_PAID`.

Система должна поддерживать полный цикл работы с данными:

- загрузку и сохранение данных;
- контроль качества данных;
- подготовку признаков;
- обучение и сравнение нескольких моделей;
- сохранение артефактов и отчётов;
- inference на внешнем CSV-файле.

## 2. Источник данных

Источником является датасет Ethiopian Insurance Corporation, который загружается через `kagglehub` или локальный CSV-файл.

В проекте предусмотрены два сценария загрузки:

- основной сценарий: загрузка исходного датасета из внешнего источника и разбиение на временные батчи;
- локальный сценарий: режим `bootstrap-local` для CI и офлайн-проверки на файле `examples/ci_training_sample.csv`.

Временная колонка: `INSR_BEGIN`  
Целевая колонка: `CLAIM_PAID`

## 3. Что прогнозируется

Модель предсказывает вероятность наступления целевого класса для каждой строки входного датасета.

На выходе inference формируются:

- `predict_proba`  - вероятность положительного класса;
- `predict` - бинарное решение с учётом выбранного порога классификации.

## 4. Организация data pipeline

Основной pipeline состоит из следующих этапов:

1. Загрузка датасета и объединение CSV-источников.
2. Преобразование времени и генерация временных батчей.
3. Сохранение сырых батчей и строк в SQLite.
4. Расчёт метрик качества данных для новых батчей.
5. Построение ассоциативных правил на бинаризованных признаках.
6. Очистка данных и подготовка признаков.
7. Обучение моделей и временная валидация.
8. Сохранение артефактов моделей, метрик и markdown-отчётов.
9. Формирование сводного отчёта.
10. Применение лучшей модели к внешним данным.

## 5. Data Quality и валидация данных

Контроль качества данных реализован на уровне батча и отдельных признаков.

В проекте рассчитываются следующие проверки и агрегаты:

- доля пропусков;
- количество уникальных значений;
- отношение числа уникальных значений к размеру батча;
- тип признака по схеме данных;
- статистика по батчам для последующего мониторинга.

Результаты сохраняются:

- в таблицу `data_quality` в SQLite;
- в итоговый markdown-отчёт `reports/dq_report.md`;
- в графики и EDA-материалы в директории `reports/figures/`.

Дополнительно используются правила очистки:

- удаление признаков с высоким уровнем пропусков;
- удаление признаков с избыточной уникальностью;
- принудительное исключение отдельных колонок, например `OBJECT_ID`.

## 6. Проектирование модели

### 6.1. Рассматриваемые модели

В проекте сравниваются две модели:

- `CatBoostClassifier` для работы с табличными данными и категориальными признаками;
- `MLPClassifier` как нейросетевая baseline/alternative модель.

### 6.2. Обработка признакового пространства

Для моделей используется единый подход к выделению признаков из схемы данных с исключением:

- временной колонки;
- целевой переменной;
- признаков, удалённых на этапе data quality/cleaning.

Далее выполняется отдельная подготовка под каждый тип модели:

- для `CatBoost` сохраняются категориальные и числовые признаки в формате, удобном для бустинга;
- для `MLP` используется пайплайн с импутацией, кодированием категориальных признаков и масштабированием числовых признаков.

В preprocessing поддерживаются:

- `SimpleImputer`;
- `OneHotEncoder`;
- `StandardScaler` или `MinMaxScaler`.

### 6.3. Гиперпараметры

Для `CatBoost` в конфигурации рассматриваются:

- `iterations`;
- `depth`;
- `learning_rate`;
- `l2_leaf_reg`;
- `scale_pos_weight`;
- `loss_function`;
- `random_seed`.

Для `MLPClassifier` в конфигурации рассматриваются:

- `hidden_layer_sizes`;
- `activation`;
- `solver`;
- `alpha`;
- `batch_size`;
- `learning_rate_init`;
- `max_iter`;
- `early_stopping`;
- `random_state`.

### 6.4. Валидация моделей

Валидация построена как time-based split:

- `train_ratio = 0.70`;
- `val_ratio = 0.15`;
- `test_ratio = 0.15`.

Для сравнения моделей используются:

- `accuracy`;
- `precision`;
- `recall`;
- `f1`.

Основная метрика выбора: `f1`.  
Дополнительно подбирается рабочий порог классификации из списка `candidate_thresholds`.

## 7. Сохранение артефактов

Проект сохраняет:

- сериализованные bundle-артефакты моделей в `artifacts/models`;
- отчёты по validation runs в `reports/models`;
- сводный DQ-report в `reports/dq_report.md`;
- историю запусков, конфигов и метрик в таблице `model_validation_runs`;
- сырые данные, батчи, DQ-метрики и ассоциативные правила в SQLite.

Это позволяет воспроизводить результаты, сравнивать модели и использовать лучшую выбранную модель в inference-сценариях.
